# Phase 15E — financial documents and transactional email

This is a local implementation contract, not legal tax advice or staging mail acceptance.

## Financial documents

The product calls the purchase document an **Order Receipt / إيصال طلب** and the adjustment document a **Refund Receipt / إيصال استرداد**. Neither is represented as a statutory tax invoice or statutory credit note. **TAX/VAT POLICY: PRODUCT/LEGAL DECISION PENDING.** No rate, jurisdiction, registration identifier, tax-inclusive rule, or legal invoice requirement is assumed. A historical nonzero `orders.tax_total`, if present, is shown only as a recorded order value.

`financial_documents` stores an immutable order/refund source key, unique human-readable ULID number (`JCEC-OR-YYYY-…` / `JCEC-RR-YYYY-…`), customer name/email, locale, amount/currency, full rendering snapshot, issue time, PDF location and SHA-256. Database uniqueness on source key, refund ID and number plus order-row locking make repeat and concurrent issuance converge on one document. There is no ordinary update, delete or regenerate API, and Eloquent rejects update/delete of issued rows; direct database administrators still require separate operational controls. Numbers are not allocated by row counts. No new PDF dependency was added: the existing mPDF installation renders branded Arabic RTL or English LTR content and stores it on the configured **private** `JCEC_FINANCIAL_DOCUMENT_PDF_DISK` (default `local`). Public disks are rejected. API metadata never returns a disk/path. Downloads stream only through authenticated, owner-scoped or explicitly permissioned backend routes.

Issuance follows successful Order `Completed` provisioning (including manually approved and zero-total orders), not cart creation, pending payment or rejected proof. An after-commit callback generates the PDF so PDF failure cannot undo access/payment truth. Eligible old completed Orders can issue on demand from their existing Order/OrderItem snapshots without rewriting history. The document snapshots order number, settled method where recorded, line titles/types/quantities/base prices/discounts/net totals, coupon snapshot, order totals and customer name/email. It never reads current catalog price, promotion date, coupon definition or package composition. Old rows with missing optional snapshot fields render only the available values; older Orders without a locale snapshot default to Arabic.

A completed Refund receives a distinct linked Refund Receipt. The original purchase receipt remains unchanged. The adjustment captures refund reference, completion time, amount, affected item snapshots when selected, original purchase receipt reference and remaining net based on recorded paid/completed refunds. Pending/rejected refunds cannot issue completed-refund documents. Marking a refund completed means an authorized operator recorded manual processing; the application does not perform a bank transfer.

## Transactional email

The existing certificate-approval workflow also records a separate `certificate_approval_granted` message when Admin approval commits. No rejection email is claimed because that workflow has no rejection transition.

`transactional_deliveries` is a durable logical outbox. Unique `event_key` prevents a second logical message for registration, order creation/completion/cancellation, a particular rejected payment, a particular completed/rejected refund or a particular issued Certificate. Safe payload metadata contains only customer name, order reference and amount/currency; it never holds proof paths, internal notes, reset tokens, answers or message bodies. The recipient address and `ar`/`en` locale are snapshotted when the event is recorded. Commerce uses `orders.customer_email` and `orders.locale_snapshot`; registration/certificate uses current user email and `users.preferred_locale`. New registration and checkout submit the active interface locale; changing language while authenticated updates the account preference. Legacy accounts/orders default to Arabic. Password-reset email continues through Laravel Password Broker to the current account email and is not duplicated in the commerce outbox.

Event rows are written inside the authoritative domain transaction. Dispatch occurs after the outermost commit. A queue job sends Laravel mail, tracks queued/sending/sent/failed state, attempts and safe exception class. `sent` means the configured mail transport accepted the send call, **not** that the recipient mailbox received it. Queue retries use 60/300-second backoff, max three attempts; successful records are no-ops on duplicate jobs. If dispatch fails after commit, the queued row remains for operational recovery. Admins with explicit `transactional_deliveries.retry` may retry the same failed row, or a queued row older than ten minutes. A crash after provider acceptance but before DB status update remains an SMTP exactly-once limitation and needs provider-side idempotency/delivery evidence; do not present queue status as guaranteed inbox delivery. The order page exposes only transactional commerce state, not password-reset details. Privileged retry is audited; routine send attempts belong in the delivery log.

Configured queue workers and failed-job monitoring are required in staging/production (`php artisan queue:work --tries=3`; review `failed_jobs` and use deliberate retry procedures). Local `MAIL_MAILER=log` or test `array` mailer is not delivery acceptance. Set a real provider, approved sender identity and SPF/DKIM/DMARC as applicable, then verify Arabic/English welcome, password reset, order, refund and Certificate mail with a real mailbox, plus worker restart/retry and bounce monitoring. **REAL TRANSACTIONAL MAIL: ENVIRONMENT_PENDING.**

For the post-commit dispatch interruption window, periodically run `php artisan transactional-deliveries:dispatch-stale`. It re-enqueues up to 100 logical deliveries still `queued` after ten minutes; repeated jobs remain delivery-row idempotent. A `sending` row is not automatically requeued because SMTP acceptance might be uncertain and requires operator investigation.

## API and authorization

- Student `POST /api/v1/me/orders/{order}/financial-documents` issues missing eligible historical documents; `GET /api/v1/me/financial-documents/{document}/download` streams only the owner's PDF.
- Admin `POST /api/v1/admin/orders/{order}/financial-documents` and `GET /api/v1/admin/financial-documents/{document}/download` require `financial_documents.view`.
- Admin `POST /api/v1/admin/orders/{order}/transactional-deliveries/{delivery}/retry` retries commerce Order deliveries only; it requires `transactional_deliveries.retry` and matching Order ownership. `transactional_deliveries.view` controls order-response delivery metadata. Welcome and Certificate delivery failures remain visible through the database/failed-job operations rather than this Order UI. These new permissions are given to the coded Admin baseline, not Sales Support, Content Manager or Instructor.
- Order APIs include safe `financial_documents` metadata; Admin Order responses include delivery metadata only when permitted. Never build a public storage link from metadata.
