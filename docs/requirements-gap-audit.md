# JCEC Academy requirements gap audit

Audited 3 October 2026 against `C:/Users/gaza1/Downloads/JCEC_Academy_Platform_Requirements_AR.docx` (the original Arabic functional/technical specification), the current repository, `docs/frontend-api-contract.md`, and `docs/frontend-development.md`. This is a code-and-test audit, **not** a penetration test or production-environment certification. No product behavior was changed. The original document uses headings and tables rather than stable numbered requirement IDs; references below cite its heading (`§`) or table (`T1`–`T6`) and row name. Its “future expansion”, “later”, “if enabled”, and “optional” qualifiers are preserved.

**Decision:** not ready for a public production launch. Public self-registration/recovery, required commerce features and transactional email, legal/public content, reporting, the complete course-file authoring workflow, and the certificate-rule conflict remain unresolved. Passing automated tests does not substitute for authenticated Arabic/English desktop/mobile browser QA or production configuration evidence.

## Reading the matrix

Each row is one independently testable requirement or a tightly coupled set of subfields within the same original requirement. `B` = backend evidence; `F` = frontend evidence; `A` = authorization/security; `T` = automated test evidence; `M` = manual browser QA. A file basename denotes a file in `app/`, `resources/js/`, or `tests/` as appropriate; the full path is given for less obvious evidence. `—` means no implementation or no identified test, not proof that the framework lacks the capability. `P0`/`P1`/`P2`/`P3` are launch-plan priorities, not status values. `COMPLETE` means an end-to-end code workflow exists and is exercised automatically; it does **not** mean final manual QA is signed off. `QA_PENDING` is reserved for an implemented path whose known decisive browser verification is missing. Codes `A0`–`A5` in the authorization column are defined after the matrix.

## Known-gap and integrity verification

### Curriculum resources and file workflows

`LessonResource` supports arbitrary `type`, `file_path` or `external_url`, `is_downloadable`, and order. The admin POST/PATCH endpoints in `LessonResourceController` accept only strings (`StoreLessonResourceRequest`, `UpdateLessonResourceRequest`); there is no multipart upload or admin resource-file download route. `AdminLessonResources.vue` explicitly supports only external links. A trusted server operator could place bytes under the configured private `lesson_resources` disk and then save a matching `lesson-resources/...` path, but that is not a content-manager browser workflow. `LessonResourceFileService` checks path syntax, realpath containment, existence, downloadable flag, and sends `nosniff`/private headers; `Me/LessonResourceDownloadController` requires current course access and published lesson/active section. This is **P0** if downloadable course files are sold/advertised.

This does not prove a real browser multipart upload, reverse-proxy/PHP size limit, or cross-browser blob download. Never serve private disks through `storage:link`.

**Broader-than-UI route:** `/api/v1/admin/courses` is callable by instructor accounts with seeded `courses.create`/`courses.update`; `CoursePolicy` constrains own-course update and own instructor assignment, but the Phase 14 instructor UI is read-only. This is not an observed cross-course IDOR; it is a product-permission mismatch to decide before launch. `/me` commerce routes allow any authenticated role to purchase for its own account; the original role table calls purchasing a visitor/student action, so decide whether staff purchases are acceptable. There is no blanket `admin` role middleware; controller policies are the actual boundary. Feature/policy tests cover major refusal paths, but no external penetration test occurred.

### Focused security findings

| Severity | Finding and concrete evidence | Recommendation |
| --- | --- | --- |
| High | **Paid video protection is unverified and app-level enforcement stops at metadata.** `StudentLearningLessonResource` returns raw `video_url`; `VideoLesson.vue` assigns it directly to native `<video src>`. If the configured media URL is a public/static object, users can share it outside access checks. The actual production media host was not available for testing. | Require signed short-lived media URLs or authenticated streaming at the hosting layer; test expired/suspended and copied URLs. |
| Medium | **Original certificate issuance rule conflicts with deployed behavior.** Original § certificates requires admin approval and configurable progress/final-quiz/assignment gates; `CertificateEligibilityService` checks all published lessons only and `/me/.../certificates` permits self-issue. | Medium | **Permission reseeding can silently remove custom role grants.** `RolesAndPermissionsSeeder` calls `syncPermissions()` for all five built-in roles. | Review role-permission diff and back up before any production seed; do not blindly rerun. |
| Medium | **File malware/active-content controls are not established.** Assignment/support allow Office/archive formats, and downloads return user-supplied original names (`AssignmentFileService`, support service/download controllers). | Low | **Currency validation checks shape, not ISO membership.** `CommerceCatalogService::currency()` accepts any three letters (`XYZ`), although it refuses missing/ill-shaped config and never silently defaults. | Validate configured currency against the approved supported list during deploy/startup. |

No confirmed Critical finding, mass-assignment/role escalation, answer-key leak before permitted result visibility, internal-note leak, payment-proof IDOR, draft-course leak, or historical snapshot regression was found in the inspected paths and existing tests. This is a bounded code review, not proof that such defects cannot exist. FormRequest `validated()` arrays and policies guard privileged mutations; `StudentQuizAttemptResource` gates score/correct IDs by attempt state/visibility; student support message and attachment queries filter internal content. CSRF uses the web login route and Axios XSRF cookies; production domain/cookie settings still require validation. Error responses under `APP_DEBUG=true` would expose internals, so production must disable it.

### Commerce, learning, certificate and schema invariants

- Money columns in course/package/order/payment migrations use `DECIMAL(12,2)`; `OrderCheckoutService` and `PaymentReviewService` use `Brick\Math\BigDecimal` and string snapshots. No float-based order arithmetic was identified. Currency is required from `JCEC_COMMERCE_CURRENCY`; missing config blocks checkout. Discount calculation is deliberately zero in checkout, which exposes R26/R27 rather than a rounding regression.
- Checkout locks the cart and has unique `(user_id,idempotency_key)`; duplicate key returns the original order. Package membership snapshots live in `order_item_package_courses`; order item stores title/price/duration and `OrderAccessProvisioningService` reads those snapshots, not current package composition. Paid and Completed are distinct: approval stamps Paid and calls provisioning in one DB transaction; provisioning sets Completed and is idempotent on the unique purchase-entitlement key.
- `enrollments` has unique `(user_id,course_id)`; many historical grants remain possible. `purchase_entitlement_key` is unique; valid grants, suspension and expiration are centralized in `CourseAccessService`. Historical grants survive catalog edits. `CourseProgressService` counts published lessons in active sections; it does **not** count quizzes/assignments as course completion, consistent with the later rule.
- Certificate issuance locks enrollment/active key; nullable unique `active_key` enforces one active certificate per learner/course, while revoked certificates retain history and require explicit reissue. It rejects archived/deleted courses, suspended enrollment, no access, empty applicable curriculum, or incomplete published lessons. This is internally consistent but **does not match the original configurable/admin-approved eligibility requirement**; R47/R48 need an explicit product decision. Verification of revoked tokens reports revoked status; old PDFs remain privately downloadable.
- Other key constraints: unique review `(user_id,course_id)`, package membership `(package_id,course_id)`, lesson progress `(enrollment_id,lesson_id)`, quiz attempt `(quiz_id,user_id,attempt_number)` plus unique active key, assignment attempt `(assignment_id,user_id,attempt_number)` plus unique active key. Assignment index uses a short explicit name to fit MySQL. Foreign keys generally restrict historical commerce/course deletion and cascade owned transient children. `order_item_package_courses.course_id` is nullable and `nullOnDelete`; historical title/order remain, but provisioning then refuses a permanently deleted course. No migration was changed.
- Concrete scale concerns: `Admin/AssignmentSubmissionController::index()` loads **all** submissions plus users, files, graders and full grading-event histories with `get()`; this is the clearest unbounded management endpoint. `Instructor/WorkspaceController::curriculum`, `quizzes`, `assignments` and admin curriculum/quiz lists also use unpaginated `get()` for whole-course nested data; this may become large for long courses. `CourseProgressService::summaries()` loads every published lesson and matched progress for the current 15-enrollment page; bounded by page but large curricula can still be expensive. Public ratings use multiple correlated `withCount`/`withAvg` subqueries per course rather than N+1; benchmark with representative catalog volume before changing. User/order/payment/support lists are paginated; instructor option picker is paginated. Do not claim a performance incident without production-like measurements.

## Frontend, i18n and test quality

Vue guards initialize session and check roles/permissions; the API client handles 401 and one 419 CSRF refresh/retry. Major pages have loading/empty/error paths and many mutation busy flags. Catalog filters are URL-synchronized where implemented. Protected downloads use authenticated blob requests rather than public anchors. Risks requiring real UI testing: admin curriculum reorder on touch/keyboard, rating selector keyboard/RTL, grading corrections, moderation dialog focus, support long conversations and mobile operations lists. `VideoLesson.vue` uses native controls but no explicit quality/speed selector or automatic checkpoint. Most frontend-owned text is in Arabic/English dictionaries, but API validation exceptions are English strings (e.g. `StoreLessonResourceRequest`, payment/assignment services), so Arabic error presentation is mixed-language. Brand slogans are intentionally fixed; user-generated text should not be translated.

Automated coverage is broad: 421 Laravel tests / 1,924 assertions and 319 Vue tests (34 files) passed in this audit. Tests exercise checkout idempotency, payment/provisioning, ownership, lesson access, quiz answer visibility, assignments, certificate eligibility/PDF, reviews, support, policies and instructor scoping. Many Vue tests mock API responses; they do not prove browser cookies, multipart upload, PDF rendering, mobile layout, accessibility, or actual third-party media. The first unconstrained Vitest run had a Windows worker crash while Laravel tests ran concurrently (311 tests passed before abort); isolated rerun with `--maxWorkers=2` passed all 319. Treat this as CI reliability evidence, not a product test failure.

## Original requirements vs later scope

**Original but missing:** registration/recovery, public instructor/about/FAQ/contact/legal content, several catalog/detail filters and sections, coupons, invoices, email, reporting/export, file-resource upload, configurable/admin-approved certificate rule, admin settings/audit, student profile, path/favorites. **Useful enhancements not established as original launch requirements:** CDN, dedicated monitoring platform, video DRM, external analytics, automated malware scanner (security recommendation rather than document feature). **Explicitly later/conditional:** electronic payment provider selection, multi-currency expansion, WhatsApp/SMS, live/hybrid if enabled, watermark when needed, library expansion, optional sequential gating. However the existing package detail already labels `is_sequential` products “sequential”: any such product offered at launch must enforce the promise or be relabeled. Do not sell/advertise a deferred feature as active.

Specifically, the original document **requires** reports, email and in-app notifications, coupons and an order refund state/process; it **defers or conditions** external payment integration and live sessions; it does **not** establish instructor commissions or standalone live chat as launch requirements. Lesson Q&A/discussion and a course group link are separate original requirements (R22/R42), not proof of a full chat feature. WhatsApp/SMS is explicitly a later enhancement.
