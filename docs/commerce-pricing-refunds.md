# Phase 15D — pricing, coupons and manual refunds

This is the Phase 15D local implementation contract, not staging acceptance or a claim that a bank refund occurred. `JCEC_COMMERCE_CURRENCY` remains the only currency authority. Amounts are `DECIMAL(12,2)` and all backend money calculations use Brick Math, not floats. No gateway, invoice, receipt, commerce email or report was part of Phase 15D; Phase 15E adds neutral financial receipts and transactional mail separately in `financial-documents-email.md`.

## Authoritative pricing

`CommercePricingService` resolves both Course and Package pricing for catalog resources, cart and checkout. The stored `price` is the regular/base price. The new nullable `promotional_price` is the only scheduled discount price; legacy `compare_price` is merchandising metadata and does not change payable totals. Both `discount_starts_at` and `discount_ends_at` must be supplied with the promotional price, the end must follow the start, and the promotional price must be below regular price. Incomplete or malformed legacy/database configuration is safely inactive. Dates use the application's UTC timezone; the interval is **start-inclusive, end-exclusive** (`start <= server now < end`). The client clock never determines the payable price.

Public Course/Package resources expose the current `price` from the engine, a structured `pricing` object with regular/active prices, savings, active flag and active promotion end, and a current compare price only while the promotion is active. Admin editing reads `pricing.regular_price`; the historical compare field is separately available to Admin. Cart summaries use the same engine; the checkout transaction locks the cart, products and applicable coupon, recalculates, and requires the submitted `expected_total` and `expected_coupon_code` to match the authoritative snapshot. A mismatch returns HTTP 409 `pricing_changed` with the new safe totals; no order is created. An invalid/expired coupon returns field validation and the cart is refreshed. The same user-scoped checkout UUID returns its original order without recalculation or duplicate grants.

Orders snapshot regular line price in `order_items.unit_price`, promotional and coupon reductions in separate columns, combined line discount, final line total, subtotal, total discount, total and currency. They also snapshot coupon code/type/value and keep the coupon ID for accounting. Catalog or coupon edits never rewrite an existing order, item or package-course snapshot. Earlier orders keep their existing totals and zero-discount history; the migration does not reinterpret them.

## Coupon rules and reservation

Codes are trimmed and uppercased before storage and lookup, with a unique normalized code. One coupon per cart/order. The coupon applies **after** scheduled promotional pricing to only its eligible, currently payable lines. Scope is all products, selected Course IDs, or selected Package IDs; unknown IDs are rejected by Admin validation. Fixed discounts are allocated in stable cart order and capped by eligible line balances; percentage discounts are rounded half-up per eligible line. Final totals cannot be negative. Active flag, window, minimum pre-coupon payable order amount, total/per-user limits, scope and value are checked on apply and again inside final checkout. Editing/deactivation affects future application, not historical snapshots.

Applying a code to a cart does **not** consume usage. Checkout creates a durable `reserved` redemption within the locked transaction; reserved plus consumed records count against usage limits to prevent overselling. Manual payment rejection leaves the order open and reservation in place so the buyer can resubmit proof. Successful payment approval and access provisioning atomically change the redemption to `consumed`. A genuinely zero-total checkout directly provisions without a fake payment and consumes any coupon in that transaction. Cancelling an unpaid order releases its reservation. Abandoned pending orders require authorized operational cancellation; there is no implicit expiry policy. A completed refund never restores coupon capacity, even when the order becomes fully refunded.

## Manual refunds and access

`refunds` is a durable manual financial record (`pending`, `completed`, `rejected`) with amount/currency, category, optional internal note/reference, explicit access effect, selected item IDs and actors/timestamps. Creating a refund only reserves refundable balance; it does **not** assert that a bank or wallet return occurred. Authorized staff must separately mark it completed after manual processing, or reject it. Order locking serializes initiation/processing, and completed plus pending refunds cannot exceed verified paid payments in the order currency. Rejected refunds release reserved balance. Amount must be positive; a final refund must explicitly select the full access effect. A final refund cannot be opened while another refund is pending, preventing premature revocation; process or reject pending records first. The refunded order status is set only when cumulative completed refunds equal the paid amount.

For full refunds, completing the refund revokes only purchase AccessGrants whose source is an OrderItem of the refunded Order; Enrollment is never blindly suspended/deleted. Any independent valid grant remains valid. Partial financial-only refunds preserve access. Partial item refunds require explicit OrderItem IDs and an amount exactly equal to their snapshotted net totals, cannot select an item twice, and revoke only their purchase grants. Selecting a Package item affects all grants created by that Package purchase, not arbitrary individual Courses; the immutable historical Package Course snapshot and sequential thresholds remain unchanged. Historical Certificates remain issued and are not implicitly deleted/revoked. Future access checks continue through `CourseAccessService` and the existing explicit certificate revocation workflow.

Permissions are `coupons.view`, `coupons.manage`, `refunds.manage`. They are included in the Admin role through the existing permission seeder, not automatically in Sales Support, Content Manager or Instructor. Student cart/order APIs are owner-scoped. Admin Order visibility alone exposes only safe refund fields; internal note, staff IDs and external reference require refund-management permission. Audit records include coupon create/update/activation and refund initiation/completion/rejection/access revocation with allowlisted identifiers and amounts, never internal notes.

## Staging gate

Local automated tests and production build do not constitute release acceptance. Staging must verify time boundaries in UTC; bilingual desktop/mobile price display; coupon apply/expiry and limited concurrent checkout against MySQL; manual payment approval; zero-total provisioning; partial/full refund with another valid grant; Package sequential access; certificate preservation; Admin versus Sales Support/Student permissions; protected media; and financial reconciliation by an authorized human. Existing Phase 15B P0 environment/legal/browser gates remain open. Phase 15E implements neutral commercial receipts and transactional commerce email locally; tax/legal policy, real delivery and staging acceptance remain pending. Financial reports remain unimplemented.
