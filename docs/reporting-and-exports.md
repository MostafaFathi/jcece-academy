# Phase 15G — operational reports and exports

This is a local implementation contract, **not** staging acceptance, a statutory revenue statement, or a tax invoice policy. The original requirements call for sales by day/month/Course/Package, learner and completion counts, ratings and quiz success, manual/pending payments, instructor performance, coupon usage, an Admin dashboard, and Excel/CSV/PDF exports of main data. Course views and “low-performing” definitions are still unimplemented tracking/product decisions (R67). Campaign attribution beyond a consumed coupon is not claimed.

## Common boundaries

- `from` and `to` are local dates in **Asia/Hebron**, defaulting to the last 30 local calendar days. Start is inclusive and the selected end day is inclusive in the UI; internally this is `[local start at 00:00 converted to UTC, local day after end at 00:00 converted to UTC)`. The range is capped at 366 days. Sales `period=day|month` groups transaction timestamps after conversion back to Asia/Hebron. Stored timestamps remain UTC.
- `course_id`, `package_id`, `instructor_id`, `currency`, status and payment method are validated and rejected on irrelevant report families. Sort is server-controlled; screen pages hold 25 rows. A synchronous export is allowed only when the full filtered result is at most 500 rows; it starts at page one independently of the visible page.
- Money comes from historical `DECIMAL` snapshots and uses decimal-safe arithmetic. Monetary summary/trend rows are **separated by currency**. `JCEC_COMMERCE_CURRENCY` is the current checkout authority; historical mixed-currency rows remain separate.
- New `reports.view` and `reports.export` permissions are granted by the additive seeder to Admin only. Sales Support and Content Manager do not inherit them. Instructor reports allow only owned Course, learner, rating and quiz data; they do not expose financial reports or exports. All boundaries are enforced on the server.

## Metric definitions

| Metric | Source / inclusion | Exclusions and date |
| --- | --- | --- |
| Gross Sales | Sum `orders.total` for `paid`, `completed`, `refunded` Orders with `paid_at`; fulfilled zero-total Orders count. | Pending, awaiting payment, cancelled and missing `paid_at` excluded. Date = `paid_at`. Completed Refunds do not reduce Gross Sales. Operational sales only, not accounting revenue. |
| Discounts | Sum immutable `orders.discount_total` for the same paid Order set. | Never recomputed from current Course/Package prices or Coupon definitions. Promotional/coupon components remain in Order Item snapshots. |
| Refunds | Sum `refunds.amount` with `status=completed`. | Pending/rejected excluded. Date = `processed_at`, even when the purchase was in an earlier period. |
| Net Sales | Gross Sales minus completed Refunds, per currency. | Can be negative for a period with old-purchase refunds. No unapproved product-level refund allocation or tax assumption. |
| Order Count / AOV | Count the Gross Sales Order set. AOV = Gross Sales / count, decimal rounded half-up to two places. | Zero-total Orders count; empty set has 0.00 AOV. |
| Sales trend | Same paid Order and completed Refund sets, bucketed by their respective event timestamps in Hebron local day/month. | Every bucket/currency has Gross, Discounts, Refunds and Net separately. |
| Course purchases | Direct Course `order_items` on paid Orders, grouped by Course/currency using immutable line `total`. | Package lines never count as additional Course sales. No Package allocation or Instructor commission. |
| Package purchases | Historical Package `order_items` on paid Orders, grouped by snapshotted title, Package ID and currency; count purchases/users, line gross/discount. | No current Package membership/price read; product-level net after unallocated refunds is not asserted. |
| Coupon redemptions | Consumed `coupon_redemptions` joined to paid Orders, grouped by `orders.coupon_code_snapshot`/currency; discount sums `order_items.coupon_discount_amount`. | Current Coupon edits and later Refunds do not rewrite historical usage. No campaign-channel attribution. |
| Learners / Enrollments | Enrollments with `enrolled_at` in range; count unique users per Course. Detail shows status, latest grant source/expiry, any presently valid grant if not suspended, and current curriculum progress. | Enrollment may remain after expiry/revocation. Package access is separate from direct purchase. Current progress comes from `CourseProgressService` over current active/published lessons, **not** a historical curriculum snapshot. Stored `completed_at` defines completion state. |
| Active learners / New students | Dashboard active learners are distinct users with a non-suspended Enrollment and presently valid grant. New students are Student-role accounts created in default 30 local days. | Current access is not a historical active-student count; account creation is not purchase/activity. |
| Completion | Course report counts stored `completed_at` among selected enrollment cohort and divides by selected Enrollments for completion percentage; Dashboard reports cohort enrollments/completions for 30 days. | Does not infer certificate eligibility. |
| Rating | Only non-deleted, `published` moderated Reviews. Rating report dates by `published_at`. Course cards use all-time published average/count, matching public aggregate. | Pending, rejected, hidden and deleted excluded. |
| Quiz pass / score | Submitted Attempts with `submitted_at` in range; passed count/rate and average stored `percentage`. | In-progress/expired excluded; current Quiz pass-score edits do not reinterpret historical `passed`. No answer keys, answers, private files or grading notes selected. |
| Instructor performance | Owned Course count; distinct learners and Enrollments in selected period; Instructor drills into own Course/learner/rating/quiz reports. | No commission, payout, or Instructor balance. |
| Payment/Refund operations | Payment rows grouped by persisted status/currency, date = `payments.created_at`; Refund workflow rows grouped by status/currency, date = `refunds.created_at`. | Workflow counts are not Gross/Net Sales. No payment proof path, gateway response, internal Refund note/reference. |
| Top direct Courses | Count paid direct Course Order Items within default 30 local days; dashboard shows top five by count. | Package entitlements are not extra Course purchases. View counts/low-performance score are not fabricated. |

## Exports and privacy

Admin reports support CSV, XLSX (OpenSpout 5.12) and PDF (existing mPDF). Exports rerun the **same validated service and filters**; they never trust client-calculated figures. CSV is UTF-8 with BOM and `fputcsv` escaping. Values starting with `=`, `+`, `-`, `@` after optional leading whitespace/control characters receive a leading apostrophe before CSV/XLSX writing. XLSX stores string cells, not formulas. Sales trend and monetary summaries are included in all formats. PDF is generated synchronously in memory with Arabic/English direction, DejaVu font, filter dates and generation time; it is not stored. XLSX uses a temporary file deleted after response. The 500-row cap protects synchronous rendering; larger exports need a separately reviewed queued/private lifecycle if demand is measured.

Every report has an explicit column allowlist. No password, token, session, private path, payment proof, Quiz answer/key, Assignment file, Support body, audit secret, or internal note is exported. Accepted Admin export requests enter `audit_events` as `report.export_requested` with actor, report type, format and safe date-filter summary only; this does not prove the browser finished receiving the file. Datasets are never logged. Instructors cannot request Admin exports, and no public download URL is created.

## Acceptance gates

Before running the additive `RolesAndPermissionsSeeder` in staging, export/compare actual grants. No migration or analytics table was added. Staging must inspect MySQL query plans/timings on representative volume before raising caps. The daily/monthly trend iterates eligible Orders/Refunds through a cursor for exact DST-aware local buckets without materializing all rows; high volume may warrant a reviewed asynchronous architecture. Verify Arabic PDF/CSV/XLSX visually and through real browser accounts. Reports do not resolve **TAX/VAT POLICY: PRODUCT/LEGAL DECISION PENDING**, **PROTECTED VIDEO PROVIDER: ENVIRONMENT_PENDING**, **REAL TRANSACTIONAL MAIL: ENVIRONMENT_PENDING**, **EDITORIAL CONTENT REQUIRED**, or **LEGAL CONTENT REQUIRED**.
